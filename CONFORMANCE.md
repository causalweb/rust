# Implementation and conformance report

Status: Experimental, source preview; no complete deployment conformance claim

Specification: `0.1.1-experimental`, exact commit in [SPEC_REVISION](SPEC_REVISION). Vector revision: `0.1.4`. The independent runner revision is pinned in [CONFORMANCE_REVISION](CONFORMANCE_REVISION). A passing fixture is evidence for that scenario, not certification of an entire class.

The `conformance_adapter` example implements the separate [`causalweb/conformance`](https://github.com/causalweb/conformance) runner's JSON Lines profiles. It runs the 32-case evidence-verification profile through this library's verifier, the 17-case prefix-evaluation profile through its verifier, exact position parser, and `Snapshot` lineage evaluator, the three-case `context-reduction-v1` profile through the public carrier reducer, the 11-case HTTP client-confirmation profile through the public HTTP parsing and confirmation APIs, and the 15-case fixed-cut `http-observer-v1` profile through the public observer API. The separate `transport_conformance_server` example runs the 7-case raw loopback `http-transport-server-v1` profile through the same observer API after preserving repeated HTTP/1.1 request fields in an `http::Request`. The client profile explicitly excludes cross-origin redirect forwarding because that requires an HTTP agent. The observer and transport profiles use ephemeral evidence and synthetic fixed-cut snapshots; neither is a generic server, storage adapter, or deployment conformance claim. The adapters do not expose local validation diagnostics or receive network trust.

## Deliberately not claimed

- **Prefix Issuer:** no reusable durable source log/outbox adapter or storage fault-model report exists. The POSIX test fixture covers one local file and injected pre-issuance interruption only. The signer requires a caller-established commitment point and caller-managed globally unique `jti` values. It cannot prove their truth or uniqueness.
- **Prefix Verifier:** no reusable durable projection/frontier adapter or power-loss recovery test exists. A narrow SQLite test verifies separate source fact/outbox and projection response/frontier transactions through rollback and close/reopen; it is not a deployable adapter or a power-loss model. The file-backed fixture exercises reconstruction after a defined process-termination boundary only. A false snapshot supplied by an adapter can cause false satisfaction.
- **Complete HTTP Server or Client:** the optional Axum adapter is an unverified route helper, not a complete network server. There is no streaming/cancellation integration, browser CORS verification, full conditional-request integration, or default redirect policy for an actual HTTP agent. The core helpers themselves do not perform redirects or network requests.
- **Durable independent-service interoperability:** the peer has file-backed loopback evidence in both directions, including defined process-termination boundaries. Rust additionally has a narrow local SQLite transaction test, but no transactional, authenticated, deployable cross-language source-to-projection service or database/power-loss recovery demonstration exists. Node.js crypto alone would only be a signature cross-check.
- **Production readiness or security audit:** no external audit, external pilot, comprehensive fuzz campaign, load characterization, or stability commitment.

## Operational policy

Every verifier configures positive byte/count/depth limits and a positive maximum evidence lifetime. There are no implicit trusted issuers, domains, audiences, or subjects. Clock skew is explicit; tests use zero unless stated. UTC seconds determine expiry only, never causal coverage. Waiting is disabled and discovery reports zero maximum wait.

Trust is immutable during an exchange. Construct a verifier from the current trusted policy for each request or ensure an equivalent policy snapshot remains authorized through response commitment. Do not reuse `VerifiedEvidence` across policy changes. Key retirement, emergency revocation, durable history epochs, frontier repair, and log redaction remain deployment obligations.

This repository cannot declare a universal storage fault model. A future adapter report must state its storage guarantees, commitment point, propagation recovery, target/schema/contract binding, and tests around both sides of the projection commit boundary before claiming a deployment class.
